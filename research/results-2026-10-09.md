# Aquilum: verified performance findings (2026-10-09)

Pinned upstream: [Freaction/Aquilum](https://github.com/Freaction/Aquilum) at `a2ac434ba70c189a5e96e8712ec781ca608ad15c` (v0.2.6).
All changes are isolated in this repository's `experiments/*` branches. No upstream PR or `rar2` changes.

## 1. Real desktop RAM and editor response

Windows GitHub Actions [#37928860555](https://github.com/Lalalalendia/aqulium/actions/runs/37928860555) built and ran actual Tauri/WebView2 + React/CodeMirror with a deterministic 5.000 MB Markdown file.

| Stage | Sum of process working sets (MiB) | WebView2 child processes (MiB) |
|---|---:|---:|
| Editor with 5 MB note mounted | 455.8 | 385.3 |
| After 120 editor changes | 479.5 | 421.9 |
| After 140 scroll frames | 475.1 | 423.3 |
| After 10 reopen cycles | 627.8 | 586.9 |

**Caveats:** Summed working sets double-count shared pages. The rise after reopens does not prove a leak (Chrome allocator/GC may retain memory). Editor dispatch p50 71.4 ms and p95 93.0 ms for 120 programmatic changes; this is not physical key-to-pixel latency. In a repeat baseline on [#37933288639](https://github.com/Lalalalendia/aqulium/actions/runs/37933288639), p50 was 62 ms, showing runner variance.

## 3. Search normalization allocation: strongest RAM result

Root cause in `core/src/search/matching.rs`: original `NormalizedText` allocates one four-`usize` span for every normalized scalar, with capacity initially equal to input bytes.

The real native Windows test compares candidate and original in separate processes with identical 5 MB mixed Russian/English text:

| Variant | Increase in Working Set, MiB | Map capacity, MiB |
|---|---:|---:|
| Original | 135.492 | 152.592 |
| Compact four-u32 offsets | 70.168 | 65.331 |
| Sparse exceptions-only offsets | **4.832** | **0.000** |

- [#37934064733](https://github.com/Lalalalendia/aqulium/actions/runs/37934064733): compact map, **593 passed, 0 failed, 5 ignored**, plus wide-offset fallback.
- [#37934492262](https://github.com/Lalalalendia/aqulium/actions/runs/37934492262): sparse map, **592 passed, 0 failed, 1 unrelated unstable history test filtered out, 5 ignored**; Unicode parity, seeded randomized mixed-language cases passed.
- One-shot normalization timings in the sparse A/B were original 39.697 ms, sparse 22.469 ms for 5 MB. These are not repeated statistically significant latency claims.

**Critical scope:** this saves transient search RAM while matching large results; it does **not** directly reduce idle WebView2 process RAM. Sparse map is preferred candidate over 4-u32 after further edge-case review.

The history coalescing test skipped in the sparse run failed in a prior full run and does not use modified search code. An entirely separate original-only baseline control in [#37932931933](https://github.com/Lalalalendia/aqulium/actions/runs/37932931933) also reproduced an unrelated Windows 8.3-path identity failure in trash tests.

## 5. Repeatable WebView2 editor ablation: full-document scans cost time

[Windows Actions #37934824233](https://github.com/Lalalalendia/aqulium/actions/runs/37934824233): same 5 MB note, one binary, 120 programmatic CodeMirror edits per variant.

| Diagnostic mode | Dispatch p50 | Dispatch p95 | Mounted app + WebView2 summed WS |
|---|---:|---:|---:|
| Baseline | 72.6 ms | 96.4 ms | 449.3 MiB |
| Disable full BookCallout and ReaderQuote document scans | 46.7 ms | 51.1 ms | 414.6 MiB |
| Disable global outline renumbering | 71.4 ms | 84.0 ms | 425.4 MiB |
| Both disabled | 46.8 ms | 51.0 ms | 414.0 MiB |

Interpretation: repeated full-document quote scanning accounts for a substantial part of the measurable synchronous update latency on this fixture. Global renumbering is less significant for these edits. Disablement is diagnostic only; the quote feature must be preserved in the production optimization.

An independently enabled, conservative CodeMirror StateField negative fast path with tests is available in [experiments/editor-quote-fastpath-20261009](https://github.com/Lalalalendia/aqulium/tree/experiments/editor-quote-fastpath-20261009). Do not treat this as proven until its real Windows A/B completes.

## 6. Search normalization stress corpus

[Actions #37935606966](https://github.com/Lalalalendia/aqulium/actions/runs/37935606966): true release-mode Windows A/B, 5 MB documents. Transient Working Set increase of original vs sparse:

| Text distribution | Original | Sparse | Native build p50 (original / sparse), n=11 |
|---|---:|---:|---:|
| Mixed | 135.50 MiB | 4.82 MiB | 68.24 / 38.84 ms |
| Cyrillic-heavy | 90.75 MiB | 4.82 MiB | 75.92 / 56.10 ms |
| ASCII | 157.39 MiB | 4.80 MiB | 63.22 / 27.39 ms |
| Accent-heavy | 96.38 MiB | 60.88 MiB | 80.54 / 91.47 ms |
| Korean Hangul | 127.74 MiB | 58.18 MiB | 73.95 / 73.94 ms |

Sparse offsets are dramatically smaller on most text but can be slightly slower for dense Unicode exception corpora; do not claim a universal CPU improvement. These are temporary search map allocations, not background RAM.

## 7. RAM setting already in Aquilum

Aquilum's default `DEFAULT_LIVE_TABS = 3`. The editor settings UI exposes `liveTabs` from 1 to 8. Users prioritizing low RAM can choose 1, trading memory for tab remount/switch latency. The absolute memory savings with three 5 MB notes still require a real desktop A/B measurement.
