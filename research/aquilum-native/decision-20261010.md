# Aquilum Native: first measured Windows UI-memory decision (2026-10-10)

## Status of the implementation

- Native Rust adapter reuses Aquilum's production `aquilum-core::DocumentHub` and the existing version checking. Both Iced and GPUI use it.
- Iced 0.14 includes a real multiline editor, tabs, manual Save and protected Reload.
- GPUI 0.2.2 + gpui-component 0.4.0-preview2 includes a real multiline Input per tab, tabs, manual Save and protected Reload. [Its real Windows release build succeeded](https://github.com/Lalalalendia/aqulium/actions/runs/37975167896).
- Shared Rust backend tests passed on Windows and Linux. The UTF-16/UTF-8 seam is protected by roundtrip/invalid-boundary tests (7 tests total at the time).
- **No claim of GUI parity:** no automated physical keyboard/IME selection/Undo/Redo/save-and-reopen tests have been run. A visible HWND is not evidence of these behaviours.

## Actual Windows private RAM: two *editable* UI prototypes

[Completed Windows ABBA run #37975887605](https://github.com/Lalalalendia/aqulium/actions/runs/37975887605).
All 16 process launches created a real GUI window; six to twenty-six memory samples were collected on each launch. On one or three independent Unicode Markdown fixture files, two repeats per UI, same hosted Windows runner:

| Workload | Iced final private commit, MiB | GPUI final private commit, MiB |
|---|---:|---:|
| 1 MiB note | 373.86, 369.57 | **106.20, 104.73** |
| 5 MiB note | 1671.55, 1671.46 | **336.73, 338.55** |
| 20 MiB note | 1496.83 (unfinished allocation), **2562.94 (2.3GiB safety guard tripped)** | 1206.69, 1202.02 (momentary high-water 1962.25 / 1908.30) |
| Three 5 MiB notes | **2561.15, 2567.84 (both stopped at RAM guard)** | **422.09, 418.38** |

Working Set and repeated samples are recorded in the [Actions job logs](https://github.com/Lalalalendia/aqulium/actions/runs/37975887605) and uploaded `aquilum-native-editable-ui-ram` artifact. Input SHA-256 after the runs matched the before hashes.

The 20 MiB Iced 1496.83 MiB sample is **not steady state**; the other reached the protection threshold. Do not take an arithmetic mean. Above-threshold tests were deliberately killed to protect the shared runner. The GPUI 20MiB peak of ~1.9GiB also warrants investigation: the steady value alone hides allocation spikes.

The measured HWND-creation time was ~250-275 ms for both prototypes, but this is **not** first paint or readiness of the text editor; Iced allocated most of its memory AFTER HWND appeared.

## Is Iced's memory overhead its GPU renderer? No

[Windows headless Iced Content-model test #37976250570](https://github.com/Lalalalendia/aqulium/actions/runs/37976250570) constructed *only* `iced::widget::text_editor::Content::with_text` in a Rust CLI, without launching Iced GUI or allocating a graphics device:

| File | Max headless private commit |
|---|---:|
| 1 MiB | 329.12 MiB |
| 5 MiB | 1615.61 MiB |
| 20 MiB | 2524.05 MiB before construction completed; killed at safety guard |

The large allocations exist in the *text model*, before GPU rendering. Tuning Iced's GPU layer cannot fix this underlying cost. The unoptimized standard `iced::text_editor::Content` is unsuitable for large Markdown notes without replacing the text component.

## Compare against actual existing Aquilum / WebView2

[Real Windows WebView2 1-vs-3 live-tab ABBA experiment #37976097072](https://github.com/Lalalalendia/aqulium/actions/runs/37976097072) succeeded with renderer-reported staged events and process-tree samples.

After three 5 MB tabs had been opened and switched, whole **Tauri + WebView2 process-tree** private committed memory:

- liveTabs=3: 233.73 MiB and 217.29 MiB, two repeats;
- liveTabs=1: 202.81 MiB and 216.22 MiB, two repeats.

At this workload, changing the mounted live tab limit 3 → 1 saves only about 16MiB in these four measurements; the effect varies with run order and environment. No compelling case to change default `liveTabs` solely for RAM. The event stages must show actual mounted-editor counts and any UI switch latency should be separately tested.

**Important:** the current WebView and native benchmarks use *different Markdown fixture generators* and *different features*. In particular, production CodeMirror virtualizes rendering; prototype inputs do not yet reproduce full Markdown behavior. The WebView process tree 203–234 MiB and GPUI multiline 418–422 MiB for similarly sized three-tab scenarios are indicators, NOT a causal like-for-like benchmark or a promise about a reimplementation.

## Decision and next implementation boundary

1. Do NOT ship Iced's stock `text_editor` for the Aquilum large-document editor.
2. GPUI has an attractive head start over Iced at 1/5 MiB, but is **not** validated as an app-wide RAM reduction compared with current CodeMirror/WebView2. GPUI at 20 MiB is also too expensive.
3. Prototype a bounded-window, rope-backed text model with UTF-16/UTF-8-safe edit transactions, and measure true native headless model memory for 1/5/20 MiB. Keep GUI view bounded; an editor widget holding the entire note is not a solution.
4. When the new model passes Unicode, undo and stale-version tests, attach it to GPUI on a separate branch. UI needs physical pointer/keyboard and IME tests before comparing with current Aquilum.
5. Keep TypeScript/Tauri `main` as the working product; no full migration justified at this stage.

No existing user notes or production file formats were changed by these experiments.
